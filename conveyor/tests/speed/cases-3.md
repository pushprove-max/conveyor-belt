# Engine cases port to serve

Measured 2026-11-14 as `README.md` says, on the loop's machine (16 cores), each file alone through the runner. Before is
main as this card's change was built on it (172d067, a `git clone --shared` checkout outside the worktree); after is
the card's worktree. Each before and after ran at the same time, side by side, so both saw the same load. The load
average was far from usual all session: 27 to 40 in the runs below. Every run passed, every case of each file. Both
runs start from the checkout they measure (`doctor`, which `serve.test.sh`'s `follow` runs, reads the checkout it is
started in: a run started elsewhere fails `follow` on main and here alike).

A case's time is its own: from when the runner marked it started (`cases/<case>` under the run's `CONVEYOR_TEST_LOG`,
written once the case holds its slot) to when it marked it ended (`cases/ok/<case>`), polled every 0.05 s. The file's
time is from the first case started to the last one ended. Faster by is `1 - after / before` of the file's time,
rounded down. Where a file's cases moved to a new file, the after row is both files run as one run.

Two files are 50% faster (`privacy`, `reviewprompt`) and one is removed (`rereview`). Seven are not 50% faster, and
none of them can be removed: each case still holds the only check of what it tests. The rows say what holds each back.
Two things limit them all at this load:

- Every case runs pinned to one core, and with the machine full, cases also wait for a test slot. A file's time then
  follows its total CPU, not its longest chain: splitting a case into parts that run side by side adds a setup and
  often a card run to each part, so it shortens the file only when the machine has free cores. `port` shows both:
  at load 12 to 20 (the earlier session's first round) its split took it from 20.0 s to 12.0 s (40%); at load 38,
  from 39.1 s to 35.3 s (9%).
- One card's run is about 2.5 s of the engine's own CPU (some 1,200 programs, a third of them `jq`), with no wait in
  it a case file can cut. A file of single runs gets 50% faster only by running half as many.

## Shared helper ideas

- `conveyor/tests/lib.sh` `setup`: every case's pack has `tunables.live = 0.2`, so every running step brings its live
  record up to date five times a second (a sleep and a `jq` each time) whether the case reads it or not. In `adopt`,
  whose steps are held for seconds at a time, that was a third of the case's CPU (87 s to 55 s with `live: 1`). The
  default of 1, with `0.2` only in the cases that wait on a live record (`samefile.test.sh`'s), would cut every such case.
- Engine, not a test helper: one card's run is about 2.5 s of the engine's own CPU, a third of it `jq` starting up.
  `rerun`, `reuse`, `records` and `port`, and any file of single runs, get 50% faster on a full machine only if that
  cost goes down.
- `conveyor/conveyor.slowest`: it names cases by their old, unsplit times (`sameoff` 75, `adopt` 67, `resume` 53,
  `kept` 48, `checkrun` 48, `rebase` 33, `privacy` 23, `retry` 21), so the runner starts those short parts first.
  Measured again, it would start `samequeue`, `adopt`, `tests` and `port` first.
- `conveyor/tests/lib.sh` `run_case`: each case costs about 0.45 s of CPU before its own work (the `python3` that
  makes it a subreaper, and the keeper's watch, which wakes every 0.5 s). Splitting a case adds that each time.
- The load: every number above is at a load average of 27 to 40 on 16 cores. At 12 to 20 the same splits gave
  `port` 40% and `samefile` 26% (the earlier session's first round). A before and after that are to be compared
  against 50% are best measured when the machine is not full.
